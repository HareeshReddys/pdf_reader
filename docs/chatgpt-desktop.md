# Experimental Windows ChatGPT desktop bridge

Set ANSWER_PROVIDER=chatgpt-desktop in the local .env and restart the app. Open one regular ChatGPT desktop window, choose Chat and Instant, and leave its message editor empty. Keep it open and unminimized. The current implementation matches English accessibility labels and runs from this Windows source checkout with .NET Framework installed.

Start assistant mode. It captures Windows speaker output, transcribes locally, and forwards each completed speech segment verbatim to the current ChatGPT conversation. Question detection is bypassed. Incomplete segments are buffered. There is no microphone fallback or CLI fallback for this route. Any audio played through speaker output, including monitored microphone audio, is included. This is source selection, not speaker identification.

The bridge uses Windows accessibility ValuePattern and InvokePattern; it does not need clipboard or global keyboard input. Requests are serialized. A different unsent draft is preserved and reported as an error. Uncertain sends are never retried automatically. Stop/Hold discards late replies locally but cannot undo a message already submitted to ChatGPT. Keep the selected conversation unchanged while a turn is running.

The speech model warms when assistant mode starts. Accessible reply text is read using targeted UI Automation document references, with a 100 ms pause between reads (actual traversal can take longer). Changed snapshots stream directly over the helper process stdout to Electron, without the previous partial-file polling step. The overlay replaces its current partial snapshot, then shows the completed snapshot. It does not wait for completion to display text. Scheduling and accessibility traversal add delay; this is not token-level synchronization. Accessible code text may differ from original Markdown formatting. ChatGPT UI changes can break the bridge. This is not an official ChatGPT conversation API and does not guarantee one-to-two-second latency.

Overlay text cannot be selected. With click-through enabled, answer text and background pass pointer input to the underlying app; buttons, the opacity slider, and other actual controls remain interactive. Disable click-through to scroll the answer or drag/resize the window.

Validation: scripts/smoke-windows-spoken-question.cjs --chatgpt-desktop plays a synthesized CSS Grid question through actual Windows output, uses the real assistant capture and local Whisper, sends to the open ChatGPT chat, checks a partial reply in the actual overlay before completion, and compares final overlay text to the returned reply. It forbids microphone access. Latest proof is data/logs/chatgpt-desktop-e2e.json. Screen/manual question actions are separate and retain their configured provider. Remote screen-sharing exclusion is not verified by this test.

Speed benchmark: run node scripts/benchmark-desktop-chat.cjs after building. It tests three spoken questions, requires the complete question before forwarding, forbids microphone access, checks partial text before completion, and records stage timings in data/logs/chatgpt-speed-benchmark.json. Baseline is preserved in data/logs/chatgpt-speed-baseline.json. Each case uses a new worker, warmed at assistant start; it is not a distribution of long-running warm-session latency. accessibleTextToOverlayMs starts when Windows accessibility exposes the first reply snapshot, not when the first pixel appears in ChatGPT. These timings do not establish a 3?4 second guarantee.

A 650 ms end-of-speech pause was tested and rejected because it split a two-sentence question before its example instruction. The 1400 ms pause remains. Direct streamed audio through the Realtime API could remove local ASR and desktop submission, but requires separately billed API credentials; it has not been implemented or benchmarked here. ChatGPT Pro does not include general API usage.
